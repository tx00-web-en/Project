# Before Starting This Sprint

After completing the previous sprints, review your team’s progress and use the information to create a realistic Sprint 3 plan.

## 1. Team Velocity

Review how much work your team completed during previous sprints.

Use this information to:

* Understand your team’s delivery trends
* Estimate how much work may be realistic during Sprint 3
* Identify differences between planned and completed work
* Improve future planning

Velocity is useful for forecasting and planning. It does **not** prove individual productivity, individual value, or product success.

## 2. Team Capacity

Review the availability of all team members during Sprint 3.

Consider:

* Course activities
* Other deadlines
* Individual availability
* Team meetings
* Development time
* Testing and debugging time
* Time needed to learn new topics

Leave approximately a **10% buffer** in your sprint commitment. This buffer provides space for unexpected obstacles, technical problems, and additional work.

## 3. Workload Distribution

Review how work was distributed during previous sprints.

Discuss:

* Whether the workload was balanced
* Whether all team members contributed
* Whether responsibilities were clear
* Whether some members had too much or too little work
* How workload distribution can be improved

Your team should aim for fair and meaningful participation from all members.

## 4. Sprint Goal Completion

Review the goals from previous sprints.

Discuss:

* What was completed?
* What was not completed?
* Which problems affected progress?
* Which decisions helped the team?
* What should be changed during Sprint 3?

Use this reflection to create a realistic Sprint 3 Goal.

## 5. Sprint Satisfaction

Conduct a short team discussion or survey about your experience during previous sprints.

Consider:

* Team communication
* Collaboration
* Planning
* Workload
* Technical progress
* Problem-solving
* Team atmosphere

Use the results to identify improvements for Sprint 3.

# Scrum Metrics

Scrum metrics can help your team inspect progress, identify problems, and improve planning. They should be used as information for the team, not as a way to judge individual team members.

The following metrics may be discussed during the sprint:

| Metric                 | Main purpose                                          | What it does not prove                                |
| ---------------------- | ----------------------------------------------------- | ----------------------------------------------------- |
| Velocity               | Forecasting and understanding delivery trends         | Individual productivity or value                      |
| Sprint burndown        | Inspecting remaining work                             | Product success or quality                            |
| Sprint Goal completion | Understanding whether the Sprint purpose was achieved | Complete customer value                               |
| Cycle time             | Understanding flow and delays                         | Individual performance                                |
| Throughput             | Counting completed work items                         | Quality or value                                      |
| Work in progress (WIP) | Inspecting open work and bottlenecks                  | That lower WIP is always better                       |
| Defect metrics         | Inspecting product quality                            | That zero reported defects means zero defects         |
| Customer satisfaction  | Understanding user experience                         | That one score explains all outcomes                  |
| Release progress       | Inspecting progress toward a release                  | That a percentage complete means the product is ready |
| Team satisfaction      | Understanding team health                             | That a happy team always delivers value               |

You will receive more guidance about the relevant Scrum metrics in class.

## Scrum Anti-patterns

During Sprint 3, avoid the following anti-patterns:

* Planning more work than the team can realistically complete
* Using velocity to measure individual performance
* Treating metrics as complete explanations of team or product performance
* Working without a clear Sprint Goal
* Working in isolation without coordinating with the rest of the team
* Delaying frontend/backend integration until the end of the sprint
* Hiding blockers or technical problems
* Treating the Sprint Backlog as completely fixed
* Confusing activity with progress
* Ignoring code quality, usability, or testing
* Leaving reflection and documentation until the last minute
* Making changes that are not aligned with the Sprint 1 prototype without explaining the reason

# Deliverables

## 1. Frontend Code

Submit the frontend code for your application.

Your frontend should:

* Include the functionality planned for Sprint 3
* Connect to the backend API
* Follow appropriate React and JavaScript practices
* Use clean and maintainable code
* Include comments where they improve clarity
* Use responsive design
* Consider accessibility and usability
* Align with the Sprint 1 prototype and the approved project direction

## 2. Backend Code

Submit the backend code for your application, including:

* The implemented API
* Database interactions
* Server-side logic
* Registration and login functionality
* Authentication-related functionality
* Other backend functionality required by the application

The backend should follow appropriate coding practices and be tested according to the testing instructions provided in class.

More details about API testing and documentation will be provided during the sprint.

## 3. Authentication

Authentication is an important part of Sprint 3.

Your application should include the authentication functionality required by your project, such as:

* User registration
* User login
* Password handling
* Authentication state
* JWT-based authentication, where appropriate
* Logout
* Authentication error handling
* Protected functionality or routes, where appropriate

If your project requires different user permissions, you may also implement role-based access control, such as different permissions for administrators and standard users.


## 4. Integrated Application

The frontend and backend should work together as one application.

Your group should work toward verifying that:

* Frontend requests reach the backend
* Backend responses are handled correctly
* Data is displayed correctly
* Forms submit correctly
* Errors are handled appropriately
* Authentication works across the application
* The main user flows can be completed

## 5. Scrum Ceremony Insights

Your group must participate in and reflect on the Scrum ceremonies.

### Daily Scrum

Document relevant points from your Daily Scrums, including:

* What was completed
* What is planned next
* Any blockers or problems
* Important decisions or changes

### Sprint Review

Present your completed and partially completed work.

Show:

* What was achieved
* What functionality is working
* What changed during the sprint
* What remains incomplete

### Sprint Retrospective

Reflect on:

* Team performance
* Sprint Goal completion
* Workload distribution
* Team communication
* Collaboration
* Challenges and solutions
* Relevant Scrum metrics
* Team satisfaction
* Improvements for the next sprint

More information about Scrum is available through the [Scrum.org learning resources](https://www.scrum.org/learning-series/what-is-scrum/).

## 6. Team Contributions

Clearly document each team member’s contributions.

Contributions may include:

* Frontend development
* Backend development
* Authentication
* Integration
* Testing
* Debugging
* Documentation
* Design and usability improvements
* Presentation preparation
* Other relevant project work

All team members are expected to contribute meaningfully to the project.

## 7. Group Presentation

Your group presentation should take approximately **10–12 minutes**.

* **Prototype Showcase**: Begin by demonstrating the prototype developed during Sprint 1. Highlight key changes or enhancements since then.
* **Progress Discussion**: Discuss the objectives of Sprint 3, challenges faced, solutions implemented, and the overall progress made. Focus on how the sprint outcomes align with your original prototype and goals.

# Suggested Workflow

The following workflow is a general guide for Sprint 3. Additional details will be provided throughout the sprint.

## Week 5: Connecting the Frontend and Backend

During this week:

1. Conduct Sprint Planning.
2. Review the Sprint 3 Goal and scope.
3. Begin connecting the React frontend to the backend API.
4. Review how the frontend and backend communicate.
5. Identify and resolve integration problems.
6. Begin planning authentication.

Up to this point, the frontend and backend have been developed separately. By the end of this stage, your group should be working toward connecting them into one application.

## Week 6: Implementing Authentication

During this week, work toward integrating authentication into your application.

### Backend

* Design and implement user registration.
* Design and implement user login.
* Connect authentication to the database.
* Implement role-based access control if it is required by your project.

### Frontend

* Integrate the authentication functionality.
* Handle login and registration forms.
* Manage authentication state.
* Use JWT authentication where appropriate.
* Use custom hooks where appropriate.

### Deployment

You will receive more detailed deployment instructions during the sprint.

## Week 7: Integration, Testing, Documentation, and Improvements

During this week, continue working on:

* Completing frontend/backend integration
* Completing authentication
* Testing the integrated application
* Fixing bugs
* Improving frontend functionality
* Improving responsiveness, accessibility, and usability
* Completing the required API documentation
* Preparing the application for deployment

You will receive more detailed instructions about API testing, API documentation, and deployment in class.

### Frontend State Management

Use appropriate state-management techniques for your application.

Where suitable, consider:

* `useContext()`
* `useReducer()`

These should be used when they provide a clear benefit to your application. Do not add them only for the sake of using them.

## Week 8: Final Preparation

During the beginning of Week 8, focus on:

* Final improvements
* Bug fixing
* Testing
* Required documentation
* Deployment preparation
* Self-assessments
* Scrum reflection
* Presentation preparation
* Evidence of team contributions
* Alignment with the Sprint 1 prototype

Your Sprint 3 performance will be evaluated according to the following criteria.

* Backend self-assessment: **15 points**

This category evaluates participation in Scrum ceremonies and the use of Scrum practices.

### Daily Scrums: 10 Points

* Consistent participation
* Clear communication
* Reporting progress
* Identifying blockers

### Sprint Review: 10 Points

* Clear presentation of accomplishments
* Demonstration of functionality
* Explanation of progress

### Sprint Retrospective Insights: 10 Points

* Reflective analysis
* Use of relevant Scrum metrics
* Identification of actionable improvements
* Reflection on team satisfaction and collaboration

* Clear explanation
* Logical flow
* Effective communication

* Explanation of progress
